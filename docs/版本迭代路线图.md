# SketchUp Design Studio × Astra｜版本迭代路线图

文档版本：1.0　｜　日期：2026-09-15　｜　用途：分阶段决策、实施与验收

**当前决定：v1.2.1 已获授权实施；v1.3、v1.4 只做路线规划，不自动开发。** 每一阶段通过验收后再选择下一步，本文件不设虚构工期，也不预先承诺 token 节省比例。

## 1. 目标与实施流程

让 Astra 负责设计理解、空间判断与关键修正，让本地代码负责重复、确定性的建模劳动。在保留建模质量和可编辑性的前提下，减少重复上下文、重复写代码、无效工具回合和返工。

```text
v1.1.1 原始 Skill → v1.2.0 动画执行器
  ↓
v1.2.1 可靠性 + 低开销接入【本次实施】
  ↓ Gate A：SketchUp / 工作台实机验收
  ↓ 用户选择下一阶段模块
v1.3A 入口精简 + 成本基线【待决策】
  ↓ Gate B：不漏规则，成本可比较
v1.3B 高频构件库 + 项目记录【待决策】
  ↓ Gate C：同参数同结果，构件可编辑
v1.3C 局部关联修改 + 定向检查【待决策】
  ↓ Gate D：改一处不重建全案，不丢手改
v1.4A 固定机位视觉对照【待决策】
  ↓ 按真实项目需要选择
v1.4B 景观专项 / 其他软件适配【可选】
```

A/B/C 是实施里程碑，不是已经发布的子版本。可以在任何关卡暂停，继续使用已经稳定的能力。

| 阶段 | 主要收益 | 依赖 | 当前状态 |
|---|---|---|---|
| v1.2.1 | 修正完成状态，减少重复进度文本 | 已有动画运行时 | 已实施；原生验收待完成 |
| v1.3A | 减少不必要的说明加载 | 明确当前工作台与用量记录 | 待决策 |
| v1.3B | 几何算法复用，减少代码重写 | 模块路由、成本基线 | 待决策 |
| v1.3C | 减少改稿范围与失败返工 | 稳定对象记录、构件接口 | 待决策 |
| v1.4A | 改善体量、细节与表现的一致性 | 几何与局部修改稳定 | 待决策 |
| v1.4B | 按需覆盖景观或其他软件 | 真实项目需求、独立适配层 | 可选，不默认开发 |

## 2. v1.2.1｜可靠性与低开销接入

**范围：本次实施。静态/模拟测试通过不等于真实 SketchUp 已验收。**

| 编号 | 实施内容 | 验收要求 |
|---|---|---|
| R121-01 | 完成门禁核对任务 ID、方案 ID、运行时版本、已完成步数、总步数和最后一步 | 撤销最后一步后，即使缺少事件通知，也不能凭旧内存状态放行 |
| R121-02 | 完成后保留轻量观察器；撤销、重做及后续提交使旧证明失效 | 重做恢复几何后不自动恢复旧完成证明；不自动修改或重建模型 |
| R121-03 | 区分历史 completed 与当前 completion_valid | 面板明确提示“完成状态待复核”，不误导立即交付 |
| R121-04 | 新增精简状态接口，保留原全量接口 | 旧调用兼容；摘要不重复携带详细历史，错误全文仍可查 |
| R121-05 | 本地进度与模型通知分离 | 正常 70 条进度示例只通知一次完成；暂停/失败不隐藏 |
| R121-06 | 回归测试、验收清单、资源清理与发布说明 | 可重复测试；最近任务最多 16 个，清出时释放监视器 |

### 行为边界

`completed` 只表示步骤执行历史；`completion_valid` 只代表目前能否通过执行完成门禁，不表示尺寸、拓扑、视觉或法规已经合格。门禁不接管 SketchUp 原生保存，也不阻止其他插件绕过接口保存文件。

本版采用保守的同模型变更检测：检测到完成后的新提交就撤销旧证明，可能包括无关编辑；不做对象级变更归因，不宣称捕捉所有扩展的非标准修改。检查点不是全几何指纹。发生失效应重新核对模型，不改写属性、强制改状态或重复生成整案来“修复”证明。

新增精简接口是实际能力；工作台通知策略是可接入示例，不会自动改造外部工作台。模型库、项目记录、自动局部关联和视觉评分不属于本版。

### Gate A：实机验收

在空白模型和正式项目副本分别测试：加载、70 步演示、暂停/继续/单步、切速与模式、关窗重开、停止保留、重复提交拒绝、原生撤销/重做、模型切换、完成后手动编辑、保存新文件并重开。比较快速与演示模式的构件、尺寸、位置、法线、材质与可编辑性。

记录操作系统、SketchUp 完整版本、工作台版本、提交 SHA、证据和失败顺序。详细表见 [实机验收清单](实机验收清单.md)。本次可提交候选分支和草稿 PR；未通过该关卡，不标称全面实测正式版。

## 3. v1.3A｜入口精简与成本基线

**解决的问题：** 主 Skill 与重复背景占据上下文，但没有可比较的合格交付成本。

**拟交付：** 主文件保留不可破坏约束、任务识别、模块路由与验收底线；新建、局部改稿、动画、材质/视图按需读取。函数库优先短接口说明，仅在调试时读源码。主入口约 1,500–2,500 字符可作为首轮测试目标，不当成模型最优长度定论。

**验收：** 尺寸来源、单位、原模型保护、洞口、命名和真实验收都有明确入口。不允许“拆成多份后又每次全部读取”。固定任务条件，对新建、重复构件、局部修改、错误修复四类任务建立成本基线。

**需要决定：** 主要使用 Codex 会员还是 API；工作台可否记录真实 usage；是否接受现有 Skill 目录重组。没有真实记录时只报告字符、字节与调用变化，不能声称会员额度节省比例。

**风险与回退：** 过度精简会漏规则；逐条保留原规则映射与测试任务，出现遗漏回退入口，不削弱验收标准。

## 4. v1.3B｜高频构件库与项目记录

**解决的问题：** 每次重新写墙、窗框、玻璃和阵列，既耗代码输出，也容易改变实现质量。

**拟交付：** 先挑 2–3 类高频构件，建议墙段/转角、真实贯通洞口、门窗总成与重复实例；再按需求增加楼板、屋面、楼梯、栏杆。每个接口明确参数、单位、适用范围、失败条件与测试，不从万能异形生成器起步。

项目记录建议包含：schema_version、项目/模型 ID、单位和原点、楼层标高、构件逻辑 ID、宿主、尺寸与来源、组件定义/实例、材质、用户保留项、手改记录、版本与验证状态。几何容差、设计偏差和资料不确定性分别表达。

**验收：** 同参数产生等价结果；重复构件共享定义，需要差异时才唯一化；墙洞真正贯通，门窗框扇玻璃可编辑；改变宽度重新计算型材，不整体拉扁；不额外添加用户没有要求的细部。只有完成实现与测试的函数才能列为支持。

**需要决定：** 建筑/室内/景观的优先顺序，前三个高频构件，矩形与异形覆盖范围，项目记录位置。依赖 v1.3A 的路由和成本基线。

**风险与回退：** 共用组件修改可能影响多个实例；接口必须返回影响范围，不能可靠定位时不执行，保留旧模型。

## 5. v1.3C｜局部关联修改与定向检查

**解决的问题：** 改一扇窗仍可能重建大范围，丢失材质、摆位等手工调整。

**拟交付：** 稳定对象 ID、定位锚点与局部补丁。关联关系按“墙 → 洞口 → 门窗 → 玻璃/窗台/已有收边”记录，修改前比较项目基准与当前模型；共享组件要识别影响范围。

检查器默认只处理本次修改对象、必要依赖与代表构件。结果区分通过、失败、未检查、不适用；优先尺寸、实际洞口、正反面、重复共面、标签、组件共享和材质归属。薄玻璃和地形不强行封闭，包围盒重叠不直接当碰撞。

**验收任务：** 改窗宽、移墙、单实例唯一化、手动改材质后再提交。必须无叠建、无丢手改，洞口和已有附属件联动正确；失败与修复计入总成本。

**需要决定：** 哪些对象允许自动联动，哪些手改必须保留，冲突交给用户还是创建独立变体。依赖 v1.3B 的对象记录与构件接口。

**风险与回退：** 冲突时保留现状并报告，不全案覆盖；不提供无依据“设为验收通过”的快捷开关。

## 6. v1.4A｜视觉质量对照

**解决的问题：** 程序执行成功，但比例、辨识特征和最终画面仍与参考不一致。

**拟交付：** 关键视觉特征表、固定代表机位与三个检查节点：白模看轮廓/标高/空间关系；深化看门窗节奏/檐口/入口等关键细节；表现看材质尺度/方向、透视、构图与光照。

**验收：** 对照机位与视场一致；不能通过裁切、改镜头或渲染掩盖漏建。阶段或异常才截图，局部修改优先局部与必要整体图；不能压缩到看不清构造。模型预览、真实渲染、AI 表达仍分开标注。

**需要决定：** 优先参考图复刻还是方案表达；代表项目与合格样本；现有渲染引擎。几何与局部修改稳定后再推进表现。

## 7. v1.4B｜可选扩展

**景观专项：** 路网连通、地形与道路标高连接、构筑物落地、树阵实例化。由真实项目缺口决定，普通室内任务不加载整套景观规则。

**其他软件：** 复用设计意图、对象 ID、项目记录与验收策略，SketchUp、Blender 等分别做执行适配；不把 SU Ruby API 直接搬到其他软件，也不把所有软件规则放进同一个主 Skill。

**另外立项：** 视频导出、时间轴回放、整次一键撤销、跨重启恢复。它们涉及事务与资源生命周期，本路线不默认承诺实现。

## 8. token / 额度评估方法

核心指标是“每个验收合格成果的总成本”，不是第一轮输出最短。固定输入、模型、推理设置、宿主版本和验收目标；每类任务至少三次作为起点，报告中位数与范围，把失败尝试和修复也计入。更换模型或推理档位另开实验组。

记录输入、输出/推理、缓存读写（能获取时）、模型与工具回合、截图数与尺寸、失败重试、总耗时、合格率。推理已计入输出时不可重复相加。API 计费、会员额度、字符和字节数分别说明。

v1.2.1 的短 JSON 只证明减少状态文本，不代表整体 token 同比例减少。本地动画和通知策略本身不调用模型，但需要工作台实际接入，才能避免进度轮询变成模型回合。

## 9. 发布、回退与决策记录

统一流程：读取远程最新提交 → 对比基线 → 独立候选分支 → 自动化测试 → 草稿 PR → 实机验收 → 决定合并及正式版本。无授权不强推、不覆盖主分支；不提交原压缩包里的 .git、凭证或私人路径。

每次替换 Skill 先备份，更新后重启 SketchUp，避免新旧 Ruby 缓存混用。回退程序不自动回退模型，测试始终使用副本。

每轮决定记录：日期、选定功能编号、暂缓项、验收模型、成本指标、风险、回退方式、对应提交/PR、通过或不通过。新想法先进入待决策区，不自动扩张当前范围。

## 10. 依据与边界

项目源码依据为用户提供的 v1.1.1 原包、v1.2.0 动画包及前一轮审查报告。路线图的优先级和验收关卡是本项目方案，不是产品官方承诺。

- [SketchUp ModelObserver](https://ruby.sketchup.com/Sketchup/ModelObserver.html)：事务事件可能在提交时才通知，不可当成实时事务锁；回调不应修改模型。
- [SketchUp Model](https://ruby.sketchup.com/Sketchup/Model.html)：事务、属性与保存 API。
- [OpenAI Skills](https://developers.openai.com/codex/skills/)：Skill、脚本与按需参考资料的组织。

官方页面核对日期：2026-09-15。所有原生验收、真实用量对比和后续版本能力均以实际执行记录为准。
